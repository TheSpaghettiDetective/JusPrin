Simplify the printer-connect flow in the printer chat: try first, ask for a credential only when the host asks
The problem. The tool the model calls, `printer_connect` (in `PrinterSetup/PrinterConversation.cpp`, described in `Agent/ToolRegistry.cpp`), does not connect anything. It validates the arguments, opens the credential form in the panel, and returns `credential_requested`. The real attempt starts only when the person presses Submit on that form, in `PrinterConversation::connect`, which runs OrcaSlicer’s `PrintHost::test` on a thread (`OrcaPrinterBackend::connect_host`) or asks the Bambu plug-in. The outcome reaches the model a turn later, as a message the app writes into the chat from `PrinterConversation::tick`: “Connection to X verified” or “failed: …”.
This two-step shape has costs we saw in live chats on 2026-11-04 with a Klipper printer (transcripts and diagnosis in the side-session notes folder of local_06a35cc1, files `moonraker-live-chat.md`, `raspberrypi-live-chat.md`, `moonraker-skill-diagnosis.md`):

* For Moonraker the common case needs no key at all (a default install trusts computers on the same home network), yet every person goes through the form.
* The model answers the first half (“a form is open, type the key there”) without knowing what will happen, and reads the later outcome through that belief. A person who submitted the form empty got a 401, and the model said “it rejected the key”, because the outcome message does not say whether a credential was sent.
* The tool’s name and the first sentence of its description (“Connects the printer…”) say the opposite of what it does. The model called it a third time as if that were a retry; it only reopens the form.
* A successful test reports only “verified”. `Moonraker::test` reads `klippy_state` from the host’s reply and only logs it, so two Klipper printers in error state were reported the same as a healthy one and the model told both people they could send prints.

The proposed direction, not a specification. For Moonraker and OctoPrint, try the connection first with no credential, inside the tool call, bounded by the 30-second limit the app already applies, and return the real outcome as the tool’s result in the same turn. Open the credential form only when the host’s answer says a credential is needed (Moonraker 401, OctoPrint 403), returning that fact so the model knows why the form appeared. The second attempt after the form stays asynchronous, since a person typing a secret cannot be inside a model turn, but it becomes the exception, and its outcome message can say what was sent. Make the successful result carry what the host said about itself where it matters to the next step, Klipper’s state for Moonraker. Bambu always needs the access code, so its form stays first; apply the same principles there as far as they go: a name and description that say what the tool does, and an outcome message that says what was sent.
Work out the specifics yourself: how a tool call may wait on the test without freezing the panel (check how the tool coordinator runs tools and on which thread), whether an unauthenticated probe is acceptable for OctoPrint, how `klippy_state` gets out of an OrcaSlicer-owned function within the fork-stewardship rules, what the tool should be called, and what the tests and the prompt suite need. Read `agent-docs/jusprin/fork-stewardship.md` before touching any OrcaSlicer-owned file, and the connection skills under `AgentUI/src/skills/connect-*` since they describe the current flow and will need to follow the new one.
Also look for the same shape elsewhere in printer connection. The two-step form-then-attempt pattern is one place where an asynchronous step was put between the model and the outcome. Search the printer connection code and the printer chat for others where a result the app has, or could have in one call, is instead delivered later by polling or by a message, and the model is left to act in the gap. Known candidates to start from: the Bambu network search, which returns “started” and reports the first heard printer by a timed message from `watch_search`; the report card shown by count at the second failure in `connection_failed`; and the Bambu connect result, which `tick` composes from polled `DeviceManager` state plus the recorded plug-in event.
