**Should fix**

1. **The Standard model's too-long chat still shows "Something went wrong on our side"** (`web_ent/jusprin/v2/gateway.py:496-512`, ea0b788fac). Standard chats go through OpenRouter to DeepSeek. OpenRouter's documentation says a 400 for a too-long chat carries the error code `invalid_prompt`, with no `response` wrapper. If it has an `error_type` at all, it sits at the top of the body, and the matcher never reads it there. So `names_chat_too_long` misses it, and the chat lands in the "anything else" branch: the person sees our generic sentence, and we get a Sentry report. The failure is the person's, and the rule says they should get `request_too_large`. Expert chats (Anthropic's "prompt is too long") and OpenRouter's mid-reply `response.failed` are matched correctly. I checked this by reading the code against OpenRouter's documentation. Sentry has no such report in the last 14 days. The fix is server-only, so the app can ship without waiting for it.
2. **Reports of a refused app request don't say which check refused it** (`errors.py:84` `super().__init__(code)`, raised again at `gateway.py:198-201`, 29445fd705). The failure is ours, and it now reaches us. But I ran `GatewayError` and its text is only the code, so both the Sentry title and the log line read `GatewayError: invalid_request`. The specific reason, such as "The X-JusPrin-Chat header must be 32 lowercase hex digits.", is lost. The rule says the report must keep the error text.
3. **Payment success page when the browser is signed out** (`web.py:412`, 29445fd705). The person sees "This link has expired. Go back to JusPrin and open the page again." with status 410, and is not told whether the payment went through. Someone buying a credit pack might pay twice. The code treats this as the person's, but it could also be the app's web view losing its cookie, which would be ours. Unverified.
4. **A real code whose coupon set is missing from `JUSPRIN_V2_LOYALTY_OFFERS`** (`ledger/billing.py:97-98`, 65dd4972f0). The person is told the code isn't recognized, exactly as for a mistyped code. That case is our configuration, so it should come to us. Nothing is logged. Checked by reading.
5. **Subscriber checkout refused** (`web.py:397`, 65dd4972f0). If the code was used in the meantime, or the account already has a plan, the person lands back on an empty code box with nothing said. Nothing is logged, so neither they nor we learn anything.
6. **Print-report refusals, now 500** (`views.py:266`, 29445fd705). These are now reported, but Sentry drops request bodies over 10 KB, and a report with photos always is. So when the report's facts JSON can't be read, Sentry won't show the text that failed. Unverified.
