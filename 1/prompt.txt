Yes — **if you reset those values while&#x20;****`3x3_cali_rl_MINI`****&#x20;is the active project, and that reset changes the project's effective settings, I would expect autosave to create a new checkpoint containing the reset values.** Then reopening the project should *not* bring the old values back.

So your observation points to an important distinction in what happened.

From the earlier trace, the original project contains explicit overrides such as:
```kotlin
Project 3MF
  Generic ABS @System
    + bed-temperature overrides
    + adhesiveness override
```

When you open it, Orca applies those overrides to the active copy:
```
saved reusable preset
        ↓
Generic ABS @System
        +
project overrides
        ↓
active edited preset
```

If you then click Orca's **reset/revert preset values**, it may only be doing this:
```
active edited preset
        ↓ reset
saved reusable preset
```

But that does **not necessarily remove the overrides stored as project state**. In other words, there may be two pieces of state that need synchronization:
```vbnet
Active Orca preset copy       ← reset happened here
Project's stored overrides    ← may still contain old values
```

If autosave subsequently serializes the project and Orca's serialization reconstructs the project settings/override metadata from somewhere that still contains those overrides—or if the reset wasn't recognized as a project semantic edit—the next checkpoint can continue carrying them. On reopening, they get applied again.

### This changes how I'd interpret the bug

Earlier I said, essentially, *"the checkpoint correctly preserves the project settings."* That's incomplete.

The key question is now:

> **Why didn't resetting the values while that project was open cause the next checkpoint to drop those overrides?**

There are two likely failure modes:

1. **Reset isn't triggering JusPrin autosave.**\
   Orca changes the edited preset back to its base value, but our autosave observer doesn't recognize that operation as a project-setting change. HEAD therefore remains the older checkpoint.
2. **Autosave does run, but serialization retains the project's old override metadata.**\
   This is more subtle: a new checkpoint gets created, but `export_3mf()` still writes the old `different_settings_to_system` / project overrides even though the visible preset was reset.

We can distinguish these very easily by looking at the version history around the moment you performed the reset:
```perl
before reset HEAD
       ↓
reset ABS values
       ↓
Did HEAD change?
   /             \
 NO              YES
 ↓                ↓
autosave       inspect new
trigger bug    metadata.3mf
                  ↓
             old overrides still there?
                  ↓
             serialization/state bug
```

And **that is the investigation I would do next**, rather than treating the reappearance of the values as expected behavior. Your expectation is reasonable: reset them in the project → autosave the resulting project state → reopen → they should remain reset.
