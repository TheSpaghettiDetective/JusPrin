<!-- reply 2 -->
> 1. The local project store (high). When someone presses Cmd+S, JusPrin saves a version into jusprin/projects/<id>/ in the app’s data folder, not into the 3MF they opened. That folder holds a HEAD file (format 1), one record per version (format 1), and current-state.json (format 2). Inside that file is the project document (format 1), which holds the chats, tool calls, print records and region labels. Each loader accepts its exact number and nothing else (ProjectStateDocument.cpp:544, ProjectVersionStore.cpp:600).
> 
> What the person sees after a format bump: they update, click a recent project, and opening fails with “managed project state is invalid” (ProjectPersistence.cpp:405). The same happens if they go back to an older version. The failure is loud, which is good, but every project is affected.
> 
> Two smaller points in the same area:
> 
> The store builds its files with OrcaSlicer’s 3MF writer and lays each object out under a name built from Orca’s internal backup number. My guess is that a future upstream release could change that layout, but I haven’t checked whether Orca treats it as stable.
> A 3MF from someone else that carries an older project document is handled more quietly. The app renames that part to .corrupt and starts the chat history fresh.

Let's look into if the current format is flexible enough so that it can accommodate some foreseeable changes without having to break compatibility.
