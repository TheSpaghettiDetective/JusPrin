## What the sources say

**Tool count alone is not your problem**
- Anthropic's tool search docs say plain tool calling is "a better fit when you have fewer than 10 tools". They put the drop in selection accuracy at "30–50 available tools". Vendor claim, measured on their own evals, raw numbers not published. https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool
- OpenAI's function calling guide says "Aim for fewer than 20 functions available at the start of a turn", and calls it "just a soft suggestion". Vendor opinion. https://developers.openai.com/api/docs/guides/function-calling
- OpenAI's practical guide to agents says the issue "isn't solely the number of tools, but their similarity or overlap". Some teams manage more than 15 distinct tools, while others struggle with fewer than 10 overlapping ones. Vendor observation from customer work, not a benchmark. https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf (text copy: https://gist.github.com/testy-cool/86cafd426ba22e3e8c1d6d2c853506c4)

**Overlapping or ambiguous tools are the known failure**
- Anthropic's "Writing tools for agents": when tools overlap or have a vague purpose, "agents can get confused about which ones to use". Vendor opinion. https://www.anthropic.com/engineering/writing-tools-for-agents
- Anthropic's context engineering post calls bloated tool sets "one of the most common failure modes". It adds that if a human engineer cannot say which tool fits a situation, an agent can't either. It recommends a "minimal viable set of tools". Vendor opinion. https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- OpenAI recommends enums and object structure "to prevent invalid states", plus "use code where possible" and "Don't make the model fill arguments you already know". Vendor opinion. https://developers.openai.com/api/docs/guides/function-calling

**Research on showing fewer tools (measured, but at much larger tool counts than yours)**
- RAG-MCP, arXiv 2505.03275: retrieving only the relevant tools raised selection accuracy from 13.62% to 43.13% and cut prompt tokens by more than half. Preprint, run on hundreds of MCP tools. https://arxiv.org/abs/2505.03275
- "Less is More", arXiv 2411.15399: cutting 46 tools to 19 improved function selection on small edge models. https://arxiv.org/abs/2411.15399
- "How Many Tools Should an LLM Agent See?", arXiv 2605.24660: shorter adaptive shortlists gave Claude Sonnet 4.6 93.1% selection accuracy versus 87.1% with a fixed 5 tools. Preprint, May 2026. https://arxiv.org/abs/2605.24660
- Anthropic reports its tool search took Opus 4 from 49% to 74% on large MCP libraries. Vendor measured. https://www.anthropic.com/engineering/advanced-tool-use
- None of this measures an 8-tool set. It shows the direction (fewer, relevant tools help), not how big the effect would be for you.

**Workflows vs agents, and state-dependent tools**
- "Building effective agents": workflows suit "well-defined tasks" where you can hardcode the path. The routing pattern "classifies an input and directs it to a specialized followup task". It also recommends "poka-yoke" tool design: change the arguments so mistakes are harder to make. https://www.anthropic.com/engineering/building-effective-agents
- OpenAI Agents SDK: `is_enabled` on a tool can be a function of the run's context and state. Disabled tools are "completely hidden from the LLM". The docs also say this "does not replace authorization" that depends on the arguments or the resource. https://openai.github.io/openai-agents-python/tools/
  - A related SDK issue describes one tool being offered before a workflow step and a different one after it, e.g. `draft_invoice` then `send_invoice`. This is the pattern for your Add→Connect flow. https://github.com/openai/openai-agents-python/issues/4626
- OpenAI's guide says to split into separate agents when prompts collect many if/then branches, or when clearer tool descriptions don't fix the errors. Guardrails should be "a layered defense", with each tool rated by risk. Vendor opinion.

**Prompt caching (documented behaviour)**
- **OpenAI (confirmed).** `tool_choice: {"type":"allowed_tools","mode":"auto"|"required","tools":[...]}` restricts which tools can be called while you keep passing the full list, "so you can maximize savings from prompt caching". The caching guide also says to keep tool definitions, order and schemas unchanged, and to use `tool_choice: "none"` rather than removing tools. https://developers.openai.com/api/docs/guides/function-calling and https://developers.openai.com/api/docs/guides/prompt-caching
- **Anthropic.**
  - The cache prefix order is tools, then system, then messages. Changing the tool definitions invalidates the entire cache, including the conversation history. Changing `tool_choice` invalidates only the messages part.
  - `tool_choice` accepts only auto, any, tool or none. There is no allowed-subset option.
  - Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 reject `any` and `tool` with a 400 error.
  - `defer_loading` with tool search keeps the cache intact, but it lets the model find tools; it does not stop it calling them. Anthropic also says it is not worth it under 10 tools.
  - Sources: https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching and https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools
- **Gemini** has `function_calling_config.allowed_function_names`, which works like OpenAI's `allowed_tools`. https://ai.google.dev/gemini-api/docs/function-calling. A figure of "~50 tools" came up only on third-party pages; I could not confirm it in Google's docs.

## Synthesis (my recommendation)

- **Scope the tools, but compute the allowed set from state, not from the conversation's label.**
  - Change conversation: allow change nozzle, open printer settings, check connection status, connect, finish.
  - Add conversation: allow identify/add and the full printer list. Once a printer has been added, also allow check connection status, connect and finish. That covers Add→Connect→Done.
  - Change→Connect already works, because the connect tools are in the Change set.
  - Each state's allowed set should include the tools for the transitions it may take next. This is the `draft_invoice`→`send_invoice` pattern above.
- **Keep the tool list identical on every turn and restrict through `tool_choice` where the API allows it.**
  - On OpenAI, use `allowed_tools`. On Gemini, use `allowed_function_names`.
  - On Anthropic, the only way to hide tools is to change the `tools` array, which invalidates the whole cache.
  - A new conversation starts with an empty cache anyway, so you lose nothing by choosing the tool set once when the conversation starts.
  - Changing it mid-conversation (for example when Add finishes adding a printer) costs one uncached re-read of the history. For short setup chats that is cheap. If it isn't acceptable, keep all 8 tools and rely on the refusal below plus clear descriptions.
- **Always refuse in code, whatever the model is shown.**
  - The layer that owns the conversation state should reject an out-of-state call and return an explicit error as the tool result. For example: "printer_add is not available while changing an existing printer's settings; to add a different printer, finish this conversation first."
  - Don't silently ignore the call. A visible error lets the model correct itself, and it matches the repo's AGENTS.md rule that invariants are enforced by the layer that owns the decision.
  - OpenAI's own SDK docs say hiding a tool does not replace authorization, so scoping and refusal are complementary, not alternatives.
- **Reduce the overlap as well.**
  - Say in each description when not to use the tool, e.g. "Only for adding a printer that is not yet set up; never while changing an existing printer."
  - Fill in the printer you are acting on from state rather than asking the model for it.
  - Consider letting the finish tool carry the outcome so there are fewer exits to choose between.
- **Add the observed failures as regression tests.**
  - Replay the confused Change transcripts and assert that the Add tools are either not offered or refused with the guiding error.
  - Add a test that Add→Connect→Done and Change→Connect still complete.</result>
