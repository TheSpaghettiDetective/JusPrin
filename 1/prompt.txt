Short answer: yes for both APIs, but Orca only half-implements it, and this fork's connect flow doesn't use even that half. The quoted sentence is true of the PrintHost send path and of this fork's Home card today, but false as a statement about what Moonraker/OctoPrint allow.

What the two APIs offer

Moonraker exposes job state directly: GET /printer/objects/query?print_stats&virtual_sdcard returns print_stats.state (standby/printing/paused/complete/error), filename, durations, and virtual_sdcard.progress. It also has a WebSocket at /websocket with printer.objects.subscribe, which pushes notify_status_update on every change, so no polling is needed.
OctoPrint exposes the same through REST: GET /api/job (state, file, progress completion, printTime, printTimeLeft) and GET /api/printer (temps and state flags), both behind the API key. No push channel in the core API; a client polls.
What Orca implements in this tree

The PrintHost classes (Moonraker.cpp, OctoPrint.cpp) implement only test and upload. That is the path this fork's connect_host uses, and it really is fire-and-forget. OctoPrint.cpp only ever calls api/version; there is no api/job or api/printer anywhere in src/slic3r.
Separately, upstream added a MoonrakerPrinterAgent (src/slic3r/Utils/MoonrakerPrinterAgent.cpp), registered in NetworkAgentFactory alongside the Qidi, Snapmaker and Creality agents that subclass it. It has the full status machinery: query_printer_status over HTTP, a WebSocket thread that subscribes to print_stats, virtual_sdcard, heaters and fans, and map_moonraker_state into the same MachineObject state the Bambu cards use. So the code to show Idle/Printing/Offline for a Klipper printer exists.
But it is compiled out. MoonrakerPrinterAgent.cpp:2084-2099 wraps the initial status query and start_status_stream in #if 0 with the comment "disable websocket for now, as we don't use MonitorPanel for Moonraker printers yet". Only the connect handshake (/server/info) runs. There is no OctoPrint printer agent at all.
How that reaches the fork's Home card

GUI_App::switch_printer_agent picks the Moonraker agent only when the preset's printer_agent field says so. Vendor profiles set it for Qidi, Creality K2/SPARKX, Snapmaker U1 and OpenEYE; a generic Klipper preset, and anything this fork's connect_host sets up, has it empty and gets the plain Orca agent. connect_host writes print_host/host_type and never binds a device_id, so describe_device never runs for these printers and the card can only say "Sends files over Wi-Fi".
