Task:
Simplify the printer chat's connect flow for Moonraker and OctoPrint: try the connection first, inside the tool call, and ask for a credential only when the host says one is needed. Kenneth has settled the design; the decisions below are his, not open questions.

**The problem.** The tool the model calls, `printer_connect` (`src/slic3r/GUI/JusPrin/PrinterSetup/PrinterConversation.cpp`, described in `src/slic3r/GUI/JusPrin/Agent/ToolRegistry.cpp`), does not connect anything. It validates the arguments, opens the credential form in the panel, and returns `credential_requested`. The real attempt starts only when the person presses Submit, in `PrinterConversation::connect`, which runs OrcaSlicer's `PrintHost::test` on a detached thread (`OrcaPrinterBackend::connect_host`) or asks the Bambu plug-in. The outcome reaches the model a turn later as a message the app writes into the chat from `PrinterConversation::tick`. In live chats on 2026-11-04 with a Klipper printer this produced: every person going through the form although a default Moonraker needs no key; the model narrating a form it did not understand and reading the later outcome through that belief ("it rejected the key" after an empty form got a 401); a tool whose name and first sentence say "Connects the printer" while it only opens a form, so the model called it a third time as a retry; and "verified" reported for two printers whose Klipper was shut down or in error, because `Moonraker::test` reads `klippy_state` and only logs it. Transcripts and diagnosis: side-session notes of local_06a35cc1-bf6c-485d-bf62-19ee49343bbe, files `moonraker-live-chat.md`, `raspberrypi-live-chat.md`, `moonraker-skill-diagnosis.md`, `failed-scenarios-one-by-one.md`.

**Decisions (Kenneth, 2026-11-04).**

1. *Every tool call is synchronous to the model.* A tool does exactly the job its name promises and returns that job's real outcome in the same turn. `slice_start` and `project_open` already obey this: their job is to start a slice or open a project, and "started"/"opened" is the true result. `printer_connect`'s job becomes: try the connection and report what happened.

2. *The slow part runs in upstream's Job on a worker of its own.* Use `src/slic3r/GUI/Jobs/Job.hpp` and `BoostThreadWorker.hpp`: `process()` on the worker thread, `finalize()` on the main thread. Give the connection work its own `BoostThreadWorker`, not `Plater::get_ui_job_worker()`, whose queue is shared with arrange and orient and which `replace_job` empties. Delete the detached `std::thread` in `OrcaPrinterBackend::connect_host` and the polling of the verdict in `PrinterConversation::tick`. Known facts to design around: upstream's `PrintHost::test` has no upper time limit (the HTTP layer's `DEFAULT_TIMEOUT_MAX` is 0), so the fork subclass must set `Http::timeout_max(30)` on its own request to make the 30-second bound real; `BoostThreadWorker`'s destructor waits at most 10 s (`ABORT_WAIT_MAX_MS`) to join and then logs, so app exit cannot hang on a host that never answers.

3. *A tool call may hand its work to a Job and stay open.* Add to `ToolExecutionCoordinator` the one rule it lacks: a call can remain pending while its Job runs; the Job's `finalize()` marks the call finished with the result, and the existing path (`AgentHost::continue_after_tool`) delivers it to the model in the same turn. The chat shows the call in progress meanwhile. The shell's 33 ms runtime timer and `pump_tools` stay as they are: they do other jobs (project boundaries, agent-opened reports, saved proposals, ended slices, MCP polling), and removing them is not part of this task.

4. *What `printer_connect` returns.* For Moonraker and OctoPrint: try first with whatever credential the app already has for that address (today `connect_host` reuses a saved key when the address matches), with no credential otherwise. Return one of: verified, carrying Klipper's state for Moonraker (`klippy_state`, read by a fork-owned subclass of `Moonraker` whose `make_url` and `set_auth` are protected and whose `test` is virtual; no OrcaSlicer file changes); needs a credential (Moonraker 401, OctoPrint 403), in which case the credential form opens and the result says that is why; or the host's own error text, forwarded as it is. When the saved key was sent and refused, say so, so the person is not told to type a key they never had. After the person submits the form, the second attempt is the same Job; its outcome message says whether a key was sent. Rename the tool and rewrite its description to say what it does; `tests/printer_prompt/printer_tools.json` is a copy of the registry and must match. The sweep session's commit 43874e3a61 on `claude/connection-help` already adds Klipper's state to the verified message and "what was sent" to the failure message; build on what it introduced rather than writing a second subclass.

5. *Bambu stays form-first* (it always needs the access code), but gets the same principles as far as they go: a name and description that say what the tool does, and an outcome message that says what was sent. The Bambu port look (`start_port_look`) and the plug-in login are not changed in this task; they are reported on in item 7.

6. *The network search for Bambu printers.* `printer_connection_status` listens inside the call for up to 30 seconds, showing the call in progress, and returns what it heard. On Kenneth's P1S the first broadcast took 8 to 40 seconds in six measurements and once over two minutes, so the result after 30 seconds with nothing heard must say "nothing heard in 30 seconds, still listening", never "not found"; the app keeps listening and posts a message if the printer appears later. The connection instructions (skills) must say what "nothing in 30 seconds" does and does not mean. Replace `watch_search`'s timed messages accordingly.

7. *Report, do not change, the other hand-rolled waits:* the Bambu plug-in login and port looks (`tick` composing the result from polled `DeviceManager` state plus the recorded plug-in event); the printer form's option list (`std::async` plus a future checked in `tick`, around `PrinterConversation.cpp:949` and `:1199`); the report card shown by count at the second failure in `connection_failed`. For each, say whether the asynchrony is necessary (a person's action, an unbounded wait) or incidental, and what the simpler shape would be.
