What was decided (fills D1, D2, D4, and adds a frame for R2/R6/R7):

1. Append-only record, separate from visibility. Each chat keeps an append-only record of every item ever sent to the model. A request renders that record plus the new items. No item is rewritten, dropped or re-derived. What the model should still see is a lifetime flag per item, never an edit of the record. Source: Anthropic's mid-conversation system messages doc (platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages): a cleared message "stays in the array but renders nothing", must be "re-sent verbatim", and rebuilding or dropping it "is an edit to an earlier message" that fails the thinking check and breaks the cache.

2. Three roles, assigned by who speaks, never by lifetime:
   - Operator, standing: top-level `system` field / Responses `instructions`. Standing prompt and tools, written once per chat, never changed.
   - Operator, in conversation: Anthropic in-array `role:"system"` message (Opus 5.5 and 5.x, not Sonnet 5); OpenAI `developer` item. Carries BOTH situational instructions (skills, the file-load reminder if it survives) AND app observations (notes: slice finished, hand setup change, calibration handover). Justification from the doc: a user message "is treated as coming from the end user, whereas a system message is treated as coming from you, the application operator"; "state changes your application observes" is a named use case. This replaces today's "JusPrin app note, not the person's words" user-text prefix.
   - End user: `user` role carries the person's words plus what travels with them (workspace block, plate picture, file report). Kept in the record as sent (closes R4).
   - Tool results stay in their own channel (tool_result / function_call_output), never promoted; the doc forbids relaying third-party content through system messages.

3. Lifetimes: skills and the reminder clear at the next user message on Anthropic (`clear_at: "next_user_message"`, beta header `mid-conversation-system-clear-at-2026-08-21`); on OpenAI there is no clear, so they stay visible and should be kept short. Notes the model replied to stay visible on both. Thinking/reasoning is stored per chat and replayed (D1: record holds exact content as sent; pictures as blob references, never inline base64).

4. Consequences for the tracker:
   - D1 decided: exact request content as sent, thinking included, pictures as blob refs.
   - D2 decided: notes become operator-role in-conversation messages, kept in the record, never cleared; one treatment for project and printer chat.
   - D4: reminder is either deleted (standing prompt already says it) or becomes a turn-scoped system message like a skill; Kenneth has not picked between the two.
   - New R-step: project-chat notes move from user text to the operator role; printer chat's developer notes unchanged in role.
   - New R-step or part of R8: fix the tool list so `object_import` is always offered (tools come first on Anthropic; any change voids the cache).
   - Kenneth confirmed this changes model behaviour, so live prompt evals against a baseline are required after each behaviour-changing step (per his 2026-10-19 rule: last confirmed results are the baseline). Baselines needed first: OpenAI journeys (none exist) and the prompt-case set (check last confirmed model/date). Request-body logging in the harness comes before any of it.

5. Open points to record as risks: `clear_at` is beta; Sonnet 5.5/Haiku 5.5 may ignore a system message placed right after a tool result, so a note landing there needs a placement rule; OpenAI accumulates visible skill text (1.3–8.5 KB each) which is an eval question; unverified whether the top-level system field and in-array system messages may coexist in one request (the doc implies yes) and how the JusPrin Cloud gateway passes in-array system messages through in its Anthropic wire format — production goes through the gateway, so check before R7.

6. Corrections to earlier claims of mine that the tracker should not carry: Anthropic DOES accept system messages inside `messages` on 5.x models; OpenAI's `instructions` parameter inserts a system/developer message rather than sitting above both.
