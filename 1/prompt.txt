## Deviations from the brief
- **No async Django view.** Django here is 4.0.10. It iterates a streaming response synchronously on the event loop, can't take an async iterator (that came in 4.2), and never tells a view the client left. So the two streaming endpoints are a raw ASGI endpoint. They are still declared in `web_ent/jusprin/v2/urls.py`. A small router (`jusprin/v2/asgi.py`, set as `ASGI_APPLICATION` in `settings_ent.py`) finds them through Django's URL resolver and passes everything else, websockets included, to obico-server's app. The wire contract is unchanged.
- **Ports.** Kenneth's main `tsd-enterprise` stack restarted when Docker started and holds 3334, 4334, 4333 and 7379. I didn't touch it. Instead I ran this worktree's stack as compose project `jusprin-cloud`, with an untracked override file that publishes web on **3434** and nothing else. Only db, redis and web run; ml_api and object_store don't.
- **Two choices the brief left open:**
  - A missing or unknown `X-JusPrin-Request` header is a 400, same as a missing turn header.
  - Upstream 400/422 becomes 400, upstream 413 becomes 413, and upstream 404 becomes 502.
- **Langfuse.** With empty keys the SDK doesn't stay quiet: it tries to export to an empty host and logs an error. v1 has the same problem in this compose setup. The gateway checks for an empty `LANGFUSE_PUBLIC_KEY` and skips logging, so it is a real no-op.
- **Model rewrite.** For Responses, the model is rewritten in every `response.*` event that carries `response.model`, not only created and completed. The message inside `response.failed` errors is replaced too.
- **Inactive users.** Tokens of deactivated users get 401; v1 doesn't check this.

## Config shape
```json
{"aliases":[{"id":"slicer-1","label":"Slicer 1","efforts":["fast","thorough"],"default_effort":"fast",
  "backends":{
    "anthropic":{"base_url":"https://api.anthropic.com/v1","model":"claude-sonnet-5-5","api_key_env":"JUSPRIN_ANTHROPIC_API_KEY",
                 "effort_map":{"fast":"low","thorough":"high"},"headers":{"anthropic-version":"2023-06-01"}},
    "responses":{"base_url":"https://api.openai.com/v1","model":"...","api_key_env":"JUSPRIN_OPENAI_API_KEY",
                 "effort_map":{"fast":"low","thorough":"high"}}},
  "groups":[{"name":"anthropic-main","format":"anthropic","percent":90},
            {"name":"responses-trial","format":"responses","percent":10}]}]}
```
- A person's group is fixed by a hash of their user id and the alias id into 100 buckets.
- Any config mistake fails loudly at startup; percents must add up to 100.
- Locally both backends point at `http://host.docker.internal:8765/v1`, split 50/50. The test user happens to be assigned `responses`.

## Live checks against the local stack
- **Sign-in flow:** authorize with S256 on `127.0.0.1:41172` works, and the token response includes a `refresh_token`. Port 50000 is also accepted, a wrong verifier gets `invalid_grant`, and a foreign redirect host gets 400.
- **Signed-in calls:** `/jusprin/api/me/` returns 200. Models, messages and responses all work through the gateway. The fake upstream received `claude-sonnet-5-5` with effort `high`, while the client saw only `slicer-1`.
- **Streaming and credits:** events arrive one by one. Three turns cost three credits; a repeat request and a title in the same turn were free.
- **Disconnect:** when the client drops mid-stream, the fake upstream's connection gets a broken pipe.
- **Revoke:** afterwards v2 answers 401 and `/jusprin/api/me/` answers 403. The 403 is v1's existing behaviour, because session auth is checked first.

## For the client agent
- **Sign-out should revoke the refresh token** (`token_type_hint=refresh_token`): that ends both tokens cleanly. If only the access token is revoked, a later refresh grant crashes with a 500 inside django-oauth-toolkit 2.3. That is an existing toolkit bug, outside this work.
