**How dialogs are caught today.** `DPIAware::ShowModal` (`src/slic3r/GUI/GUI_Utils.hpp:203`) calls `answer_modal`, which hands the dialog to a scoped listener. The listeners are `ScopedDialogListener` and `ScopedLeastChangeAnswers`, in `src/slic3r/GUI/JusPrin/Workspace/DialogListeners.hpp`. Listeners are put in scope only:
- in `OrcaWorkspaceAdapter.cpp`: during file loads and in six tools;
- in three actions in `ShellController.cpp`.

The tool coordinator and the printer chat (`PrinterSetup/`) have no listener. A dialog is missed for one of four reasons:
1. It opens from a background event, such as a network or plug-in callback, a printer message, or `CallAfter`.
2. It opens through `show_error` (`GUI.cpp:250`), which always defers the `ErrorDialog` until after the listener's scope has ended.
3. JusPrin calls OrcaSlicer with no listener in scope.
4. It bypasses `ShowModal`: `Show()` windows such as `DeviceErrorDialog`, `wxMessageBox`, or raw wx dialogs.

The notification sweep `d0bce03db3` (`PrintIssues/NoticeKinds`, where a new notification kind breaks the build) is a good pattern for a guard, but it covers notifications, not modal dialogs.

   - A dialog with no listener in scope may still be one the person started in the classic OrcaSlicer view, and that one must still show.
   - A deferred `show_error` has to be tied back to whatever caused it.

   A useful seam idea for the connection popup (`GUI_App.cpp` ~2095-2108, the "Incorrect password" / "Connect %s failed!" `show_dialog`): have the fork's `JusPrin::Printers::record_connection_event` return whether the printer chat was waiting for that answer, and skip `show_dialog` when it was.
