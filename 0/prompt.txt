<result>## Result: full project export cost vs mesh size

All numbers are from `build/arm64` **RelWithDebInfo**, which this repo compiles at **-O0** (`CMakeLists.txt:544-548` rewrites `-O2` to `-O0` for Clang). The shipping Release config is -O3 and was not built (empty `build/arm64/src/*/Release/`; a full -O3 build is roughly an hour). Treat the absolute milliseconds as an upper bound; the ratios and the "where the time goes" split are what to trust. The earlier "170 ms / 31 KB" figure came from the same -O0 harness config, so it is comparable.

Machine: Apple M2 Pro, 12 cores, 32 GB, macOS 26.3. One sphere mesh per project, one plate, the default Bambu X1C profile from `tests/data/jusprin/harness.conf`. "Mesh size" = binary STL bytes (50 B/triangle); the in-memory `indexed_triangle_set` is about a third of that.

Findings:
- **Cost is linear, about 8.3-10.5 ms per 1,000 triangles at -O0.** A 1M-triangle project blocks the UI for ~8.3 s per timeline row; a 100k one for ~1 s.
- **The export is on the UI thread.** `OrcaWorkspaceAdapter::export_project_archive` asserts `wxIsMainThread()` (`OrcaWorkspaceAdapter.cpp:378`) and the harness confirmed `main_thread=1`; `ProjectPersistence::capture_revision` calls it synchronously from the workspace-change handler (`ProjectPersistence.cpp:172, 303-315`).
- **Almost all of it is mesh serialization, not thumbnails.** Thumbnail rendering + `publish()` + plate bookkeeping is a fixed ~95-140 ms (the 2k-triangle case: 120 ms total vs 25 ms store-only; this matches the old 170 ms for a two-plate project = 2 plates x 4 GL thumbnails). Everything above that is `_BBS_3MF_Exporter::_add_mesh_to_object_stream` (`bbs_3mf.cpp:7142`) writing vertices/triangles as XML text through `format_coordinate`, then deflating at `MZ_DEFAULT_LEVEL` (`bbs_3mf.cpp:6751`). For 1M triangles the uncompressed model part is 82.8 MB of text, compressed to 9.3 MB; the PNG thumbnails are ~60 KB.
- A second run with two harness instances overlapping (see caveats) gave the same numbers within 1%, so they are stable.

## Model copy: mesh buffers are shared, not deep-copied

Verified in code and measured:
- `ModelVolume` holds `std::shared_ptr&lt;const TriangleMesh&gt; m_mesh` (`Model.hpp:1040`) and its copy constructor is `= default` (`Model.hpp:1030`), so copying shares the buffer. `Model::assign_copy` -&gt; `ModelObject::new_copy` -&gt; `ModelObject::assign_copy` -&gt; `new ModelVolume(*volume)` (`Model.cpp:59-110, 1121-1160`) never touches mesh data. `TriangleMesh` itself holds `indexed_triangle_set its` by value (`TriangleMesh.hpp:158`), so copying a *TriangleMesh* is a deep copy.
- Measured `Model copy(plater.model())`: **0.13 ms (100k), 0.20 ms (400k), 0.25 ms (1M)**; after the copy `mesh_ptr()` of source and copy are the same pointer (`mesh_ptr_shared=1`). A deliberate deep `TriangleMesh` copy costs 0.5 / 2.2 / 6.3 ms respectively, so even a fully private copy would be cheap.
- Mutation paths are copy-on-write in the normal case: `ModelVolume::transform_this_mesh` builds a new `TriangleMesh` and `set_mesh`es it (`Model.cpp:2896-2900`). Two exceptions mutate through `const_cast` in place: `center_geometry_after_creation` (`Model.cpp:2606`) and `scale_geometry_after_creation` (`Model.cpp:2886`, commented "could only be called before the meshes ... are shared"). Both are creation-time paths; a worker export would need to be started after them, or from a deep copy.
- Hypothesis probe: `store_bbs_3mf` run on a `std::thread` from the shared-mesh `Model` copy, with `store_to_3mf_structure` plate data and `full_config_secure()` taken on the UI thread first, produced byte-identical archives (1,149,231 / 4,554,866 / 9,285,383 bytes) at the same speed as on the main thread (944 / 3,590 / 8,288 ms). `bbs_3mf.cpp` references no `wxGetApp`/GUI globals. This is one successful run, not a thread-safety proof; the thumbnails (the fixed ~100 ms) must stay on the GL/UI thread.
