No, and it shouldn’t be. They’re two different kinds of result.

An OrcaSlicer question is a warning with code orca_question, returned by settings_preview_patch. It means: this change is valid and will apply as sent, but a person making it by hand would see this question. The agent settles it before applying the patch. It can go ahead, go ahead and tell the user, or ask the user first when the answer is theirs. The guidance for this lives in the settings_preview_patch tool description in ToolRegistry.cpp, not in any prompt.

This refusal is a plain tool error, code change_failed, returned by printer_change. Nothing happened: the nozzle wasn’t changed because the unsaved printer edits couldn’t be saved to version history first. There’s no question to settle and no “go ahead” option. The model handles it like any other failed tool call. It reads the message and decides what to say, and the failed tool card already shows the person the sentence.

Two things follow from that:

There’s no specific guidance for this failure. The printer prompt (printerInstructions.ts) gives instructions after a failed connection (lines 156-157) and for settings the tools refuse (line 59). It says nothing about change_failed from printer_change, and it doesn’t mention orca_question at all. So the agent improvises here, and I haven’t measured what it does.
Making it an OrcaSlicer question would be wrong. That would mean the change applies anyway and the agent decides whether to mention it. The whole point of this refusal is that the nozzle must not change while the edits exist nowhere else. A failed save to version history is a fault to report, not a choice for the user. The useful next step is to try again. Failing that, the person can save or discard the printer edits in Printer settings, then change the nozzle.
If you want the agent to say something consistent here, the fix is one line in the printer prompt about change_failed. That would mean editing prompt text, which the original brief said another task owns, so it’s your call.
