Background (from the session that started this one):
Kenneth (JusPrin, a fork of OrcaSlicer whose built-in AI agent chats about the project) wants prompt testing to stop depending on paid per-token API models. In a 2026-10-19 session we tested the file-loaded skill a different way: we recorded the exact requests the app sends (pointing JUSPRIN_OPENAI_ENDPOINT at a local recorder), and had fresh Opus 5.5 subagents in a Claude Code session answer them. That surfaced prompt-caused problems clearly. Kenneth's reasoning: production users will often use stronger models than DeepSeek V4 Flash, testing strong models over the API is too expensive to do routinely, and the coding subscription already pays for a strong model. Those subagents read a Markdown dump and could not make real tool calls, and they knew they were being tested. Headless `claude -p` with a custom system prompt and an MCP stub fixes most of that and can be driven from the existing Python runner.

Task:
Add a backend to tests/project_prompt/run_prompt_tests.py (and, if it shares the code, tests/printer_prompt/run_prompt_tests.py) that answers each recorded step with the locally installed Claude Code CLI in headless mode, instead of POSTing to OpenRouter (model) and OpenAI (judge). The goal is prompt iteration that bills the developer's Claude subscription, not API usage.

What exists: the runner replays requests recorded from the app (tests/project_prompt/requests.json, recorded by the shell harness). It sends each one to deepseek/deepseek-v4-flash on OpenRouter (MODEL, ENDPOINT, post()). It answers read-only tool calls from recorded results, at most three reads (recorded_answer, answers_for, run_once, MAX_READS). It judges the step with JUDGE_MODEL gpt-5.5 over the OpenAI API (judge(), judge_response()). The README in tests/project_prompt explains the step rules. test_steps.py checks them offline.

Design to implement, keeping all of today's step rules:
- New flag, e.g. `--backend claude-cli [--claude-model opus]`. The default stays as today.
- Per run: `claude -p --model <m> --system-prompt <the request's instructions> --tools "" --strict-mcp-config --mcp-config <generated json> --output-format stream-json --no-session-persistence`. The 2.1.283 CLI has all of these flags; verify the exact behaviour, and whether `--bare` keeps subscription auth.
- Real tool calling through a small stdio MCP stub server written in Python under tests/project_prompt/. It exposes the 28 tools from project_tools.json with their real schemas. Read-only calls are answered with today's recorded answers. The first change call is recorded as the step and ends the run, exactly as today. Parse which tool calls happened from the stream-json output.
- Render the recorded input items (user text parts, the <workspace> block, images if the CLI accepts image input in stream-json, and the app's developer-role notes) into the prompt. Claude has no developer role, so render those notes as clearly labelled app text and say so in the README. This is the same fidelity question the README already describes for DeepSeek hosts.
- Judge on the subscription too (`claude -p --json-schema` for a yes/no verdict), behind its own flag, because changing the judge resets the baselines (see the "confirmed results become the baseline" convention in the README/handoffs).
- Run several cases in parallel with a small cap, so the subscription's rate limits aren't hit all at once.
- README: when to use which backend. Opus on the subscription measures what the prompt itself causes, and is cheap to iterate with. The app's default model is gpt-5.4-mini (OpenAIResponsesAgent.hpp), which scored about like DeepSeek in the README's model table. So a strong model can paper over ambiguities a weaker one trips on, and a small paid run on the app's default stays the pre-release check.
