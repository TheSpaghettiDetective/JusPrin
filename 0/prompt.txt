## What was observed (2026-10-12, live test on jusprin-newui d0bce03db3, model gpt-5.4-mini)

A Thingiverse model named Spiral_Vase1_SOLID.STL (85 x 85 x 150 mm, a solid meant for vase mode) was loaded with a Bambu Lab X1 Carbon 0.4 nozzle, "Bambu PLA Basic @BBL X1C" and "0.20mm Standard @BBL X1C". After the user said "It's a vase. It only needs to hold dried flowers.", the assistant made two tool calls:

1. settings_search {"limit":10,"query":"spiral vase","scope":"process","writable":true} returned {"items":[] ...}: no writable setting matched.
2. settings_get {"keys":["spiral_mode","wall_loops","top_shell_layers","bottom_shell_layers","infill_density","sparse_infill_density"],"scope":"process"} returned spiral_mode with "label":"Spiral vase","value":"0","writable":false.

The assistant then told the user it had not changed the setting "because I need to avoid guessing on the exact print style without your confirmation" and offered to enable it. It never said the setting is read-only for it. Earlier in the same conversation it had sliced the vase as a solid block (5 h 22 min, 153 g).

## What is already known from reading the code (verify it, do not take it on trust)

- src/slic3r/GUI/JusPrin/Workspace/SettingsSupport.hpp: writable_setting(key) is an allow-list of process keys the tools may write. "spiral_mode" is not in it. The comment above it says each allowed key "was traced through ConfigManipulation's normalizer and toggles and Tab's handlers; the hazard table in the tool extension guide says what each can rewrite or ask."
- src/slic3r/GUI/JusPrin/Workspace/OrcaSettings.hpp around line 132 already has a validation rule that blocks a configuration where spiral_mode is on but wall_loops, top_shell_layers, infill, support, thin walls and others are not in their vase-mode values. So part of the code already expects spiral_mode to be reachable.
- There is also a per-plate spiral mode: OrcaWorkspaceAdapter.cpp line 226 reads plate.get_spiral_vase_mode(), OrcaOutline.cpp line 134 checks plate->has_spiral_mode_config(), and AgentHost.cpp line 520 reports "spiralMode" in the applied setup.
- My hypothesis, not verified: spiral_mode was left off the allow-list because OrcaSlicer's own UI (ConfigManipulation) opens a dialog offering to change the dependent settings automatically when spiral vase is switched on, and a tool call cannot answer a dialog.

<pasted_content id="757f">
The agent could search and read every applicable setting. Writing was initially limited because changing an Orca setting can:

* Open a modal dialog and block the GUI thread.
* Silently rewrite dependent settings.
* Affect slicing, dirty state, saving, and revert behavior.
* Have different Undo semantics.
* Conflict with simultaneous GUI edits.

Each writable key therefore had to be traced through Orca’s normalizers and handlers, then tested for native UI updates, dependencies, atomic application, stale-state protection, and undo/revert behavior. See [mcp-tool-extension-guide.md (line 679)](/Users/kenneth/Projects/JusPrin/agent-docs/jusprin/mcp-tool-extension-guide.md:679).
The policy was: start with a small proven write surface, then expand key by key after real-adapter tests. This prevented the tool from hanging on dialogs or claiming one result while Orca silently produced another. The hazard audit explains those risks in [mcp-tool-extension-guide.md (line 880)](/Users/kenneth/Projects/JusPrin/agent-docs/jusprin/mcp-tool-extension-guide.md:880).
