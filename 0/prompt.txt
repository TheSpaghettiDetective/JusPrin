The proposal, confirmed by Kenneth on 2026-11-02 (also in memory file `connection-skill-per-connection-type.md`):
1. When a person tries to connect a printer in the chat, the app adds one skill to that conversation at that moment. Not before, and not for people who only pick a profile and prepare prints.
2. The skill is a text file in the repo, one per connection type (Bambu now; Moonraker/OctoPrint later, not in this task), chosen by the app from the connection type, never by the model. It holds the procedure: which tool to call, what each reported state means, and the one right next step for each, including silence, where it tells the model to ask what the person sees and wait rather than conclude. It holds no menu wording the app cannot verify.
3. The status and connect tools report the situation exactly as the app observes it (heard nothing yet, port taken, plug-in missing, cloud mode, wrong code, the host's own refusal reason). This part is already done on the base branch. The skill drives the conversation from those states; the tools never carry the procedure.
4. Improvement loop: the skill grows by pull request reviewed by a person. When the agent and the person are struggling, by a rule the app applies (a connect attempt failed twice, or the person corrected the model), the chat asks whether to send a report to the JusPrin developers; the person sees what will be sent and says yes or no. The report holds the tool states and the connection turns, never the access code or API key. Do this part last, in-app only (the rule, the ask, the preview, the payload); there is no server endpoint yet, so stop and ask Kenneth before building anything server-side.
5. Before any skill line is written for a state, that state must have been made to happen for real. Write lines only for states you can point to a real run for.
