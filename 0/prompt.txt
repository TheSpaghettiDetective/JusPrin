<result>## Summary

The "+ New" button's low‑contrast text is a real bug, but it is **not** a color-value mistake on the New button itself — the New button's CSS correctly references design tokens. The root cause is a **naming bug in the shared token-application code** (`WebShared/tokens.ts`) that silently breaks every *multi-word* semantic color variable (`primaryText`, `primaryHover`, `secondaryBorder`, etc.) across **both** HomeUI and AgentUI. HomeUI's CSS follows the documented kebab-case convention and is therefore visibly broken; AgentUI's CSS instead (non-compliantly) uses the same broken camelCase names the buggy JS actually emits, so it "looks fine" only by accident.

### 1. Where the buttons are defined

```tsx

  Import
&lt;/button&gt;
&lt;button type="button" className="button-primary" onClick={() =&gt; client.send('new_project', {})}&gt;
  + New

```

CSS rules: `/Users/kenneth/Projects/JusPrin/.claude/worktrees/figma-design-file-42aa00/src/slic3r/GUI/JusPrin/HomeUI/src/styles.css:308-341`

.button-primary {

There are **zero hardcoded hex/rgba literals** in this file (verified by grep, and enforced by a Vitest guard — see below), so the New button is *not* using a raw color — it's using a token reference that resolves to nothing.

### 2. The token file and the actual bug

Token source: `resources/jusprin/ui/design-tokens.json`, `semantic.light.action` / `semantic.dark.action`:
```
light: primary=#3A2D64, primaryText=#FFFFFF, secondary=#FFFFFF, secondaryText=#17131F, secondaryBorder=#E8DFEB
```
These values are fine (white text on the dark‑purple primary background is high contrast).

The bug is in `/Users/kenneth/Projects/JusPrin/.claude/worktrees/figma-design-file-42aa00/src/slic3r/GUI/JusPrin/WebShared/tokens.ts:125-133` (`applyAppearance`, shared by both HomeUI and AgentUI):
```ts
for (const [group, values] of Object.entries(mode)) {
  for (const [name, value] of Object.entries(values)) {
    if (typeof value === 'string') root.style.setProperty(`--${group}-${name}`, value);
  }
}
```
This writes `--action-primaryText`, `--action-secondaryText`, `--action-secondaryBorder`, `--action-primaryHover`, etc. — **camelCase, not kebab-case** — because it never calls the file's own `kebab()` helper. Contrast with the sibling functions in the *same file* that do it correctly:
- `applyPixelTokens` (line 51): `` `--${prefix}-${kebab(name)}` ``
- `applySharedStaticTokens` (line 88): `` `--font-${kebab(name)}` ``

So `--action-primary-text` (what HomeUI's CSS asks for) is never actually set. The `color` declaration is invalid/unresolved and falls back to the inherited value — `body { color: var(--text-primary) }` = `#17131F` (near‑black, set correctly because "primary" is a single word needing no kebab conversion). Result: near-black text (`#17131F`) on a dark indigo background (`#3A2D64`) for "+ New" — exactly the barely-visible pill in the screenshot.

### 3. Why "Import" looks fine — it's a coincidence, not a fix

`.button-secondary` background is `--action-secondary` = `#FFFFFF` (white, single-word, sets correctly). Its `color: var(--action-secondary-text)` is *equally broken* (also never set), so it too falls back to inherited `--text-primary` = `#17131F`. But dark text (#17131F) on a **white** background is high contrast — so the Import button accidentally reads fine, while the New button, with the *same underlying bug*, sits on a dark background and becomes unreadable. Both buttons are broken identically; only one is visually exposed.

### 4. design-system.md's stated rule

`agent-docs/jusprin/design-system.md`, "Writing UI code" (line 162-170):
&gt; **1. Never type a color, radius, font, or control size.** Every one comes from `resources/jusprin/ui/design-tokens.json`. ... The Agent page uses only `var(--…)`: `--&lt;group&gt;-&lt;name&gt;` for color, `--radius-&lt;name&gt;`, `--font-&lt;role&gt;`, `--font-code`, and `--button-&lt;recipe&gt;-padding`.

And "Runtime application in the native app" (line 215-218):
&gt; **Web:** `AgentUI/src/tokens.ts` writes the semantic colors as `--&lt;group&gt;-&lt;name&gt;` on every appearance change...

So the documented contract for a color variable name is `--&lt;group&gt;-&lt;name&gt;`, where `&lt;name&gt;` should be the kebab-cased token key — exactly what HomeUI's stylesheet (correctly) assumes and what `applyAppearance()` fails to produce.

### 5. Is this isolated or systemic?

**Systemic — it's a bug in the shared token-application utility, not a per-button typo.** Concrete evidence:

- All 10 multi-word keys in the `action` semantic group (`primaryHover`, `primaryPressed`, `primaryText`, `secondaryHover`, `secondaryPressed`, `secondaryText`, `secondaryBorder`, `dangerText`, `dangerBorder`, `disabledText`), plus `text.onAction` and `status.successOnAction`, are affected in **both** light and dark modes — 12 distinct broken CSS custom-property names, system-wide.
- In `HomeUI/src/styles.css` this currently manifests as **7 broken `var()` references**: `--action-primary-text` (319), `--action-primary-hover` (325, 326), `--action-secondary-text` (333), `--action-secondary-border` (335), `--action-secondary-hover` (340, 359).
- `AgentUI/src/styles.css` (1800+ lines) never triggers the visible symptom, but only because it uses the *same broken camelCase* names the JS actually emits — e.g. `var(--action-primaryText)` (line 1012, 1028, 1179, 1496), `var(--action-primaryHover)` (1017, 1086, 1183), `var(--action-primaryPressed)` (1022, 1187), `var(--action-disabledText)` (1173, 1192, 1465, 1505). That is itself a violation of the documented `--&lt;group&gt;-&lt;name&gt;` (kebab) convention — AgentUI's authors apparently discovered the actual (buggy) runtime variable names and coded against those rather than the documented kebab convention, masking the underlying bug instead of fixing it.
- There are **no hardcoded hex/rgba literals** anywhere in `HomeUI/src/styles.css` or `AgentUI/src/styles.css` (both are 0 per grep) — the "Never type a color" rule is otherwise followed diligently, and is mechanically enforced by `styles.test.ts`'s "carries no literal color" check in both projects.
- The native C++ side (`Brand/BrandPalette.cpp`) does contain many raw hex literals, but those are the *documented, intentional* mapping table described in design-system.md §"Retained OrcaSlicer surfaces" (`StateColor::SetColorOverrides` mapping upstream OrcaSlicer literals to semantic tokens) — not a violation.

**Testing gap that let this ship:** Both `HomeUI/src/styles.test.ts:75-87` and `AgentUI/src/styles.test.ts:79` have a test titled "asks only for variables that tokens.ts emits," but the regex only covers the *static* token groups:
```ts
/var\((--(?:font|button|project-card|printer-card|status-dot|swatch|glyph|elevation)-[\w-]+)\)/g   // HomeUI
/var\((--(?:font|button)-[\w-]+)\)/g                                                                 // AgentUI
```
Neither pattern includes `action`, `text`, `surface`, `border`, or `status` — the semantic/appearance color groups — so no test in the repo actually verifies that a `var(--action-primary-text)` reference corresponds to a variable `applyAppearance()` really sets. That's why this shipped undetected in HomeUI, and why AgentUI's workaround-via-camelCase went unnoticed as a documented-convention violation.

### Fix locus (for reference, not applied — investigation only)
The one-line fix is in `WebShared/tokens.ts:131`: change `` `--${group}-${name}` `` to `` `--${group}-${kebab(name)}` ``. That alone would fix the New button, but it would simultaneously break every AgentUI CSS rule that currently (incorrectly) references the camelCase names, so those ~15+ AgentUI `var()` call sites would need to be updated to kebab-case in the same change, and the `styles.test.ts` "asks only for variables that tokens.ts emits" check in both projects should be extended to cover the semantic color groups so this class of bug is caught by CI going forward.</result>
