## Findings

**1. What renders the panel — webview, not native**

The "Set up the agent" empty state and its full setup flow (`Continue with JusPrin`, `Use your own API key`, `Connect an AI tool you already use`) are React/TSX, packaged into a local HTML page and rendered inside a `wxWebView`:

- `SetupChooser` component: `src/slic3r/GUI/JusPrin/AgentUI/src/components/Setup.tsx:53-87` (all three CTAs live here, plus the "footnote" copy).
- Mounted from `src/slic3r/GUI/JusPrin/AgentUI/src/App.tsx:18` (`SetupChooser` import) and driven by bridge messages (`SetupStatusPayload`, `kOpenSetup`).
- CSS is **responsive**, not fixed-pixel: `.setup-card { width: 100%; display:flex; flex-direction:column; ... }` at `src/slic3r/GUI/JusPrin/AgentUI/src/styles.css:1397-1406`, with an explicit design comment right above it: `styles.css:1384-1389` — *"Agent setup. The screens replace the dock body in place, so they reuse `.pane-state`'s metrics... The setup screens are the only pane states taller than the dock... They scroll, so the actions at the bottom stay reachable."* This is flex/percentage-based, sized to whatever its host panel is (agent-pane min width is `320px`, `resources/jusprin/ui/design-tokens.json` → `component.agentPane.minWidth: 320`), not tied to a fixed viewport.

**2. The "Add a printer" dialog is 100% native wxWidgets**

`PrinterSetupDialog` (`PrinterSetupDialog.hpp:29`) is a `DPIDialog` built entirely with wxBoxSizer/wxStaticText/wxTextCtrl/custom `RoundedPanel`s (`PrinterSetupDialog.cpp:34-99`, `274-404` etc.) — no wxWebView anywhere in it. It sizes itself per-state: `dialog_width = 500` DIP (`design-tokens.json` → `component.printerSetup.dialogWidth: 500`), with per-state target heights computed in `rebuild()` (`PrinterSetupDialog.cpp:190-230`). No existing sub-webview content (photo drop is a native `wxFileDropTarget`/`FocusablePanel`, `PrinterSetupDialog.cpp:74-84, 300-327`).

**3. Current "Set up the agent" click handler**

`build_no_agent()` wires the button to `set_up_agent()` (`PrinterSetupDialog.cpp:386`, handler at `771-775`):
```
void PrinterSetupDialog::set_up_agent() {
    EndModal(wxID_CANCEL);
    wxGetApp().CallAfter([open = m_open_agent_setup] { open(); });
}
```
`m_open_agent_setup` is bound in `PrinterSetupLauncher.cpp:94` to `[shell]{ shell-&gt;open_agent_setup(); }`. `ShellController::open_agent_setup()` (`ShellController.cpp:392-399`) switches the main frame off the Home tab, un-collapses the docked `AgentPane`, and calls `m_agent_pane-&gt;web_view().host().request_setup()` — which just sends the `kOpenSetup` bridge envelope (`AgentHost.cpp:1927-1934`) to the *already-running* React app, telling it to show `SetupChooser`. So today it closes the whole modal and redirects to the main Plater view with the dock's setup screen.

**4. Existing precedent for wxWebView-in-dialog: yes, elsewhere in the repo**

There is no JusPrin precedent (`PrinterSetupDialog` is the only dialog under `GUI/JusPrin`), but upstream OrcaSlicer already does exactly this pattern: `WipingDialog` in `src/slic3r/GUI/WipeTowerDialog.cpp:366-422` is a plain `wxDialog` that creates a `wxWebView::New(this, ...)` child, adds it to the dialog's sizer (`main_sizer-&gt;Add(m_webview, 1, wxEXPAND)`), loads a packaged local HTML file via `LoadURL`, and registers a script-message bridge (`AddScriptMessageHandler("wipingDialog")`) — i.e. a self-contained webview mini-app embedded and sized inside a modal, not full-window. This is a direct architectural precedent for "reparent/resize a webview into a dialog."

However, the Agent setup page is **not** factored out as an independently-instantiable component the way `WipingDialog`'s page is. `AgentWebView` (`AgentWebView.hpp:25-42`, ctor `AgentWebView.cpp:37-`) does take only `parent/theme/workspace/persistence/availability/agent/setup` — reasonably decoupled as a class — but each instance owns a `unique_ptr&lt;Agent::AgentHost&gt;` (`AgentWebView.cpp:46-47`) wrapping `unique_ptr&lt;IAgentService&gt;` / a single `IAgentSetupService` (`AgentService.hpp:133`, `AgentSetup.hpp:65`). There is exactly **one** `AgentPane`/`AgentWebView`/`AgentHost` per app, owned by `ShellController` (`ShellController.cpp:204-206`) and wired into MCP discovery, conversation persistence, and the main frame's docked sizer (`ShellController.cpp:243-251`, resize handle, collapse/width persistence at `330-390`). The setup screen isn't a separate page load — it's the same running single-page app switching internal state via the `kOpenSetup` bridge message.

The code already documents this exact tradeoff: comment at `PrinterSetupDialog.cpp:366-368`:
&gt; *"The Agent panel's own empty state is a page in the Agent web view and cannot be hosted in this native modal, so the card is drawn here and its action opens that panel's setup flow rather than a second one."*

**5. Assessment: not a simple resize/reparent job**

The page content itself is responsive-ready (flex/`width:100%`, already designed to fit a narrower dock than the 500px dialog) — that part is not the blocker. The blocker is architectural singleton coupling:
- Only one `AgentHost`/`AgentWebView` exists app-wide; spinning up a second one for the dialog would need a second `IAgentSetupService`/MCP-discovery-writer or risk state conflicts, since these are unique/shared singletons tied to the main shell's workspace and persistence (`ShellController.cpp:204-206, 226-231`).
- The alternative — `wxWindow::Reparent()`-ing the *existing* `AgentWebView` out of the docked `m_center_sizer` into the modal dialog and back — is technically possible (wx supports reparenting, and `WipingDialog` shows webview-in-dialog works fine as a pattern) but isn't something this code currently does anywhere, and reparenting a live wxWebView with an open native-messaging bridge across window hierarchies (plus interaction with the dialog's own modal event loop, `EndModal`/`ShowModal`) is a materially bigger, riskier change than "same class, new parent, new size" — it touches `ShellController`'s docking/width-persistence code, the dialog's modal lifecycle, and possibly platform-specific webview reparent quirks, not just CSS/sizing.

**Bottom line**: the page/CSS is responsive enough to render nicely at dialog width. But "reuse the same page" is a bigger job than a resize — it requires either introducing a second Agent-setup webview/service instance (state-duplication risk) or reparenting the singleton `AgentPane`'s webview into the dialog and back (untested pattern here, though precedented by `WipeTowerDialog.cpp`'s dialog-hosted webview). This is exactly the tradeoff the code's own `PrinterSetupDialog.cpp:366-368` comment calls out as the reason today's implementation redirects instead.</result>
