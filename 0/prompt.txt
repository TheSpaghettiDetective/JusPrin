Background (from the session that started this one):
JusPrin is an AI-piloted fork of OrcaSlicer (C++17, wxWidgets, CMake). On 2026-10-22 Kenneth decided:
- JusPrin checks for its own new versions against the release list of TheSpaghettiDetective/JusPrin on GitHub.
- Download opens the release page; installing from inside the app comes later.
- JusPrin's first v2 version is 2.0.0, kept separate from OrcaSlicer's SoftFever_VERSION (2.4.2), which 3MF files, profile updates and config upgrades read.

That check is built on branch claude/no-orca-update-window: it reads GitHub's releases API about 10 s after start and then daily. OrcaSlicer's own update check is handed to it through a small GUI_App seam (app_update_check).

The repo's CI is still OrcaSlicer's, so no JusPrin 2.x release exists on GitHub yet; the only releases are JusPrin 1.x (tags v1.3.0, jusprin/v1.4.0) and a stale "nightly-builds" pre-release. Kenneth prefers reports in plain English.

Task:
Design, then build what Kenneth approves: how JusPrin publishes its own app releases and built-in profile updates. JusPrin's update check already reads these releases, but nothing publishes them yet.

Start from:
- `.github/workflows/build_all.yml`, `build_orca.yml` and `publish_release.yml`. Every upload step is gated to `github.repository == 'OrcaSlicer/OrcaSlicer'`. Files are named `OrcaSlicer_…`. `publish_release.yml` only runs for the actor in the repo variable `RELEASE_PUBLISHER`, which is SoftFever. The MSIX step (`scripts/msix`) uses OrcaSlicer's Store identity.
- `src/slic3r/GUI/JusPrin/Updates/` on branch `claude/no-orca-update-window`. `Version.hpp` holds JusPrin's version (2.0.0) by hand. `ReleaseFeed.cpp` reads tags `vX.Y.Z` or `jusprin/vX.Y.Z` from GitHub's release list. Drafts and pre-releases are skipped. Release notes come from the release body.
- Profile updates: OrcaSlicer's `PresetUpdater` (`src/slic3r/Utils/PresetUpdater.cpp`, around line 666) asks `AppConfig::profile_update_url()`, which is `check-version.orcaslicer.com/profile`, sending the vendor and `SoftFever_VERSION`. Preferences > Updates' "Update built-in printer and filament profiles" row (`sync_system_preset`) turns it on. Its detail text says "Only the profiles JusPrin ships", which is not what happens.

Answer in plain English, with 2 or 3 options and a recommendation:
1. CI. How the Windows installer and zip, macOS dmg, Linux AppImage and Flatpak get built and attached to a JusPrin GitHub release with a `vX.Y.Z` tag, published by Kenneth.
2. Version. How the tag and `Version.hpp` stay in step: a CI check, or the version derived from the tag.
3. Signing and notarisation. What each platform needs, and what accounts or secrets Kenneth must provide.
4. Profiles. Keep OrcaSlicer's profile server and reword the Preferences row, or publish JusPrin's own profile bundles (for example as release files) and point the updater there. Cover privacy: what each request sends.

Follow `agent-docs/jusprin/fork-stewardship.md` for any change to OrcaSlicer-owned workflow or source files: prefer fork-owned workflows or small neutral switches, and record the rebase evidence.

Done means: the recommendation reported. Then, once Kenneth approves, the workflows and code on a branch cut from `claude/no-orca-update-window`, verified by a dry-run release to a draft, without publishing anything public. Don't push or publish a release without Kenneth's explicit go-ahead.
