## JusPrin agent paths

1. **Auto-answer mechanism.** `ScopedModalAnswers` (`JusPrin\Workspace\ModalAnswers.cpp:25`) is consulted from `DPIAware::ShowModal`. That covers every MsgDialog, MessageDialog, RichMessageDialog, InfoDialog and UnsavedChangesDialog, but not wxFileDialog or wxColourDialog. `show_error` escapes it, because it uses `CallAfter` (GUI.cpp:251).
2. **Where the scopes are installed.** Only four places in `OrcaWorkspaceAdapter.cpp`: `open_project` (1707), `import_objects` (1801), the place-object unit fix (983, always No) and `delete_items` (1905). **No settings or preset path uses them.**
3. **`settings_apply_patch` bypasses by refusing.** `apply_settings` (2408) calls `Tab::load_config` (Tab.cpp:1246). That does `reload_config()` + `update()` and **never calls `on_value_change`**, so none of section 3's prompts, or their side effects, can fire. The `update()` dialogs are refused at preview time instead:
   - `check_process_dialogs` (`OrcaSettings.hpp:184`) mirrors section 2 one-for-one.
   - `check_filament_dialogs` (278) covers the 0.5 volumetric speed and the temperature-pair check on save.
   - `check_printer_dialogs` (307) covers firmware retraction.
   - The writable key lists (`SettingsSupport.hpp:18-73`) exclude prime tower, timelapse and support filaments.
   - One consequence: the agent can set layer_height below the printer's min_layer_height with no Adjust/Ignore prompt. Preview only mirrors ConfigManipulation's max check.
4. **`printer_setup` bypasses by discarding first.** `apply_printer_setup` (624) refuses unless the call says `unsavedEdits:"discard"` (ToolExecutionCoordinator.cpp:650). It then discards edits before `Tab::select_preset`, so UnsavedChangesDialog normally has nothing to ask about.
5. **`project_open` bypasses by discarding, loading silently and auto-answering.**
   - It discards preset edits, then loads with `"&lt;loadall&gt;"` (no ProjectDropDialog).
   - `answer_load_question` (1657) answers "Save" with No, too-large and too-small from the request, and any other MsgDialog with No. The substitutions, modified-G-code and 3MF version dialogs are therefore auto-dismissed.
   - `update_print_fff_config` prompts raised while loading the project are also answered **No**. For spiral mode that means spiral gets turned off.
   - Those ConfigManipulation dialogs have no caption, so the recorded "decision" title is just the generic "%s info" (MsgDialog.cpp:399). The decision log can't tell them apart.
6. **Edge case in `project_open`.** If `save_project_choise` is remembered as "yes", `close_with_confirm` never calls ShowModal and **saves** instead of discarding (Plater.cpp:14736). For an untitled project that can open an unintercepted file dialog.
7. **Not agent-reachable.** Filament count, colour, AMS sync and the named-printer menu (`Shell\SetupCommands.cpp`, FilamentMenu, PrinterMenu) are UI-driven and show Orca's dialogs normally.
8. **Gap: process-only switch with an edited filament.** In a `printer_setup` call that changes only the process, preview counts filament edits only if the filament names change (OrcaWorkspaceAdapter.cpp:601-604). But `Tab::select_preset(print)` opens UnsavedChangesDialog for any edited filament (Tab.cpp:6057). No scope is installed, so the modal blocks the agent.
9. **Gap: `printer_add`.** `OrcaPrinterBackend::add_printer` → `install_and_select_printer` → `Tab::select_preset` (SetupCommands.cpp:482) has no unsaved-edits pre-check and no scope, so an edited printer, process or filament preset opens UnsavedChangesDialog. Separately, after a printer switch, section 2 dialogs (e.g. "Too large layer height") can open from `TabPrint::update` without being intercepted (occasional).
10. **`printer_change` (nozzle) is safe.** `change_named_printer_nozzle` (`Printers\NamedPrinters.cpp:383`) refuses when the printer preset has edits, and writes the profile directly without going through `select_preset`, so no dialog.</result>

## How a 3MF's origin is decided

- **Step 1 (`src\libslic3r\Model.cpp:387-409`):** `PrusaFileParser::check_3mf_from_prusa` (`3mf.cpp:287-339`). The file counts as PrusaSlicer only if both hold:
  - there is **no** `3D/_rels/3dmodel.model.rels` (Bambu/Orca projects always have one);
  - in `3D/3dmodel.model`, a metadata item whose name contains "Application" has text containing "PrusaSlicer".
  - Side note: the "saw Application" flag is never reset, so any later text in the model containing "PrusaSlicer" also counts.
  - Result: `From_Prusa`, loaded by `load_3mf(..., check_version=true)`.
- **Step 2 (everything else):** `load_bbs_3mf` then `_handle_end_metadata` (`bbs_3mf.cpp:3946-3962`):
  - `Application` starting with `BambuStudio-` or `OrcaSlicer-` marks it as a Bambu-family file and records that version.
  - An `OrcaSlicer` tag that parses as a version marks it as a Bambu-family file and records the Orca version.
  - If the Orca version is present, it wins as the file version and the file is `From_Orca`. Otherwise the file version comes from `Application` (`:1425-1434`).
  - Final mapping: Orca tag → `From_Orca`; Bambu-family without the tag → `From_BBS`; anything else → `From_Other`.

| Real-world file | Type | file_version |
|---|---|---|
| Printables / PrusaSlicer project | From_Prusa | — |
| MakerWorld / BambuStudio (no Orca tag) | From_BBS | Application version, 4-part packed |
| Upstream Orca before the tag (Application `OrcaSlicer-2.x`) | From_BBS | e.g. 2.3.1 (≤ 2.3.2) |
| Upstream Orca with the tag, and this fork | From_Orca | tag value (this fork: 2.4.2) |
| Fusion, 3D Builder, SuperSlicer, Cura, other Orca forks writing their own Application name | From_Other | — |

## Part 2 — How JusPrin reaches Orca popups

### The hook
- **Hook location (in an Orca-owned file):** `GUI_Utils.hpp:89-93` declares `answer_modal()`. `DPIAware&lt;P&gt;::ShowModal()` at `GUI_Utils.hpp:203-210` calls it first and returns its answer without showing the dialog.
- **Where it's defined (fork-owned):** `JusPrin/Workspace/ModalAnswers.cpp` (`answer_modal` → `answer_through_scope`). It uses a stack of nested scopes, works only on the GUI thread, and records the dialog's **title** and the answer.
- **It reaches MsgDialog classes:** `wxDialog::ShowModal` is virtual, so `DPIAware::ShowModal` overrides it even when called through a base pointer. `MsgDialog` derives from `DPIDialog` (`MsgDialog.hpp:58`). So `MessageDialog`, `RichMessageDialog`, `ErrorDialog`, `WarningDialog`, `InfoDialog`, `DownloadDialog`, `PrintHostSendDialog`, `show_info` and `show_error` (`GUI.cpp:249-285`) are all intercepted. So are `UnsavedChangesDialog`, `GuideFrame`, `ProjectDropDialog`, `StepMeshDialog` and `SelectMachineDialog`.
- **Not intercepted:**
  - `wxMessageBox`, `wxMessageDialog`, `wxFileDialog`, `wxDirDialog`, `wxColourDialog`.
  - `ProgressDialog`, which derives from plain `wxDialog` (`Widgets/ProgressDialog.hpp:27`). This is the "Loading…" window.
  - `ZUserLogin`, which derives from `wxDialog`.
  - `DPIFrame` windows such as `SecondaryCheckDialog`.
  - Anything shown non-modally with `Show()`, and anything queued with `CallAfter` or an event after the scope has ended.
- **Two gaps worth knowing about:**
  1. `close_with_confirm` skips `ShowModal` entirely when `save_project_choise` is saved (`Plater.cpp:14736`). If that saved choice is "yes", it calls `save_project()` even inside a "discard" scope, and an untitled project then gets a raw file dialog.
  2. The records keep only the title. The Agent would see "JusPrin - Load 3MF" answered "no", but not the message text.

## Part 3 — Branding
