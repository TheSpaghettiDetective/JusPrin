## 3. Unclear or missing in the rules, and what I did

- **Product refusals with no table entry.** The table covers only AI-request failures. Many outcomes here look like decisions a person made, for example:
  - attachment too_large, unsupported_type and not_text (1467-1475);
  - the 10 MiB note (3179-3181);
  - chat_provider_removed;
  - cli_missing;
  - busy while a reply streams;
  - the races where Stop or cancel arrives after the reply has ended (1925, 2080, 2486, 2723).

  I judged them unexpected, as the brief says, and ranked the clear product rules (file size and type) low. They probably need table entries rather than code removed.
- **Tool error codes.** The tool error contract (invalid_arguments, not_found, busy, needs_step, refused, failed) answers the model, not a person. The rules don't say whether a result the model reads counts as "what the person is told", or whether those codes need entries. I reported only that "failed" and every other tool failure is logged and never reported (finding 12).

# Error-handling sweep: the tool-call files (reader B)

Snapshot: commit 5e173c5e15. Paths below are relative to `src/slic3r/GUI/JusPrin/`. Every finding was checked only by reading. No code was run.

The expected-errors table lists only failures of a request to the AI. No tool failure has an entry. So, strictly, every tool failure is unexpected. I did not report the codes that answer the model's own mistakes or a state it can read again: `invalid_arguments` for bad arguments, `not_found`, `stale_workspace`, `busy`, `needs_step`, `feature_expired`, `opened_before`, and the settings corrections. ## 1. Findings, most harmful first

### 1.1 Failures inside the app go back to the model as tool results. They are never reported, and the model writes its own sentence about them.
- `Agent/ToolExecutionCoordinator.cpp:63-84` (`workspace_error_code`): this maps `WorkspaceError::Failed` to `"failed"` and `Refused` to `"refused"`.
- It is used at these call sites: 671, 702, 744, 1371, 1419, 1443, 1513, 1573, 1580, 1629, 1670, 1708, 1727, 1810, 1832, 1862, 1885, 1904, 1923, 1948, 1956, 2062, 2222, 2434.

- `Agent/ToolErrors.hpp:5-28` and `:55-59` set the policy behind this. The group "Stop and tell the person" covers `refused`, `failed`, `local_save_failed` and `cancelled`. The comment adds that "a rare failure the app has nothing more to say about keeps one generic message".
- `fail()` at `ToolExecutionCoordinator.cpp:2508-2531` records the failure and announces it to subscribers. `AgentHost::continue_after_tool` (`AgentHost.cpp:3291`) then sends it to the model.

**What the code does.** Suppose OrcaSlicer fails an export, an import, a render, a merge or a slice start. The coordinator stores the failure as the call's outcome and hands it to the model as data. Nothing reports it, and the turn goes on. ToolErrors.hpp works as a second table of decided outcomes, and nobody decided them under these rules.

**Rules it breaks.** "Let the failure stop the work and travel up unchanged." "One handler at the top of each entry point reports the failure through the one reporting function and tells the person 'Something went wrong on our side', with nothing more specific." "Do not … give it a sentence of its own."

**What goes wrong.** Take a person whose export fails because the disk is full. No report is made anywhere. The person reads whatever the model decides to say, which may be a guess or a retry. Nobody upstream ever learns the failure happened.

**Confidence:** high that this conflicts with the rules as written. Whether a tool result counts as "telling the person" is open (part 3).

- OpenAI's 429 `insufficient_quota` (billing used up; this is from what I know of OpenAI's API, not verified here) is shown as "rate limited, try again shortly", so Retry loops.
- A 402 from our own server that the app cannot read is unexpected, but the person is told they are out of credits.

**Confidence:** high for the code path. Medium for which third-party answers actually occur.

### F6. The request id and the provider's error text are lost in the transport, and nothing reports
**Where:** `OpenAIHttpTransport.cpp:48-66` and `AgentTransport.hpp:40-46`. `AgentHttpEvent` has no headers. The `request-id` or `x-request-id` response header is never captured, and `Http.cpp` stores the headers but passes none of them on.

**Also:** `AgentProtocol.hpp:274-279`. `AgentError` cannot carry a status, request id or text.

**And:** `tests/agent/test_provider_agent.cpp:582-600` ("HTTP failures are mapped to safe errors") asserts that the body is dropped ("sensitive upstream body").

Following one failure up from the chat entry point:
1. Http thread.
2. `accept_http` queue.
3. `AgentHost` tick, `ProviderAgent::poll`, then a `Failed` event.
4. `AgentHost::fail_stream` (`AgentHost.cpp:3412-3415`). It shows the invented sentence, or "The AI request failed." when there is no error.

No step calls a reporting function, and no step says "Something went wrong on our side".

**Rules broken:**
- "Keep the other side's status, request id and error text."
- "One handler at the top of each entry point reports the failure through the one reporting function."

**What a person or record sees:** a support case cannot be matched to the provider's or the gateway's own records.

**Confidence:** high.

### F7. A reply that takes more than 120 s is cut off and called a timeout
**Where:** `AgentTransport.hpp:27`, where `request_timeout_seconds{120}` becomes `CURLOPT_TIMEOUT`, the total transfer time (`Http.cpp:336`). The result is classified at `ProviderAgent.cpp:696-697`.

**What it does:** A healthy stream still producing text after 120 s is cut by the app's own limit. curl reports "Timeout was reached" and the person sees "The AI request timed out." plus Retry, after part of the reply is already on screen and recorded (`handle` → `record`).

**Rules broken:** "Do not … give it a sentence of its own." The table's `timeout` cause is "took too long to answer, or the connection to it stalled". A stream that is still flowing is neither, so the cut is an undecided failure dressed as an expected one.

**Confidence:** medium. I inferred from the 64000 `max_tokens` and adaptive thinking that a reply can last that long; I did not measure it.

## 3. What was unclear or missing in the rules and the skill

- **The table covers only requests to the AI.** Sign-in refusals (wrong code, expired code, wrong password, too many tries), the Expired sign-in, the model-list refusal and the account endpoints have no entries. The brief says anything not in the table is unexpected, so I reported them as unexpected (F9, F11). Someone plainly designed the email refusals, which are documented in `CloudAccount.hpp:141-145`. Whether they need entries, or the table was meant to cover them, is for Kenneth to decide.
- **Model-behaviour outcomes.** Tool calls fed back to the model as refusals, `malformed_tool_call`, `refusal`, `max_tokens`, pause_turn: these are deliberate designs with no entries. I grouped them in F4 rather than treating each as a separate defect.
- **Retryable flags and the person's next step.** The table names what the person can do next, but `AgentError.retryable` is set per code here, not taken from the table. The rules do not say whether that flag must come from the table. I did not report it separately.
- **The current test contradicts the rule.** The test at `test_provider_agent.cpp:582` deliberately asserts that the provider's body is not kept ("safe errors"), while the rules say to keep the other side's error text. I followed the rules (F6). Someone should decide whether provider text may hold secrets that must not reach the record.
