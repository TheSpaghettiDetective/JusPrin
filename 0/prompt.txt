## The design

The project chat's standing prompt carries principles only. Situational guidance is a skill: a `SKILL.md` file on the Agent page (`src/slic3r/GUI/JusPrin/AgentUI/src/skills/<name>/SKILL.md`, frontmatter `name` plus `trigger`) that the app adds as the last item of the one request where the model first reads about the event, never stored, never repeated. The loader exists since 1435f4c817: read `AgentHost::fire_skill` (`src/slic3r/GUI/JusPrin/Agent/AgentHost.cpp` about line 1130), the trigger names in `Protocol::SkillTrigger`, the existing `model_arrived` skill and its two firing sites (about lines 2286 and 2636), and the recorder's `"skill": true` check in `tests/shell/project_prompt_scenario.inc`. Add a trigger for this skill the same way; the host must stay indifferent to how many skills exist.

## The problem, verified in the code

- `slice_start` posts the same event as OrcaSlicer's Slice button and, without `wait`, returns `started: true` at once (`src/slic3r/GUI/JusPrin/Agent/ToolExecutionCoordinator.cpp` about line 1783). OrcaSlicer's handler then runs its validation synchronously; when validation fails (for example Bambu PETG HF on the Smooth Cool Plate) OrcaSlicer pushes a ValidateError notification, marks the plate invalid and starts nothing (`src/slic3r/GUI/Plater.cpp` about line 8075). None of that reaches the tool reply, so the model is told the slice started when nothing happened.
- With `wait: true` the call is finished by `finish_slice_waits` (about line 815), run from `pump()` on the app's periodic tick, which polls for "seen running then stopped" or "plates read as sliced for 3 seconds" or a 15-minute cap. A refusal never flips `slicing.running`, so the call sits for 15 minutes and returns `finished: false` (line 845) with no reason. The coordinator's workspace-change subscription (lines 379 to 382) already tracks `m_slice_seen_running` and `m_slice_ended`, so the same fact is tracked twice.
- `slice_report` for an invalid slice returns only validity and ids (`src/slic3r/GUI/JusPrin/Agent/ToolResults.cpp` about line 686). The reply of a finished slice has no warnings either.
- The reason is not lost in the app: `PrintIssueMonitor` (`src/slic3r/GUI/JusPrin/PrintIssues/PrintIssueMonitor.cpp`, about lines 137, 382 and 428) keeps per plate the failure message in OrcaSlicer's words, the setting key, the object and a severity, re-running OrcaSlicer's own `validate` to recover the key and object the notification lacks. The workspace adapter already records a reason at a transition for one case, `m_invalidated_by` (`src/slic3r/GUI/JusPrin/Workspace/OrcaWorkspaceAdapter.cpp` about lines 373, 637 and 719), and publishes slicing changes the coordinator subscribes to.

## What to build

**A. The fact, recorded once, read everywhere.** When OrcaSlicer declines to start a slice (its validation notice) or a run dies mid-slice (its completion event with an error), record on that plate, at that moment, why slicing did not succeed: OrcaSlicer's words, the setting key and the object when known, and which of the two it was. Put it in the workspace snapshot beside `sliced`, `estimate_status` and `invalidated_by` (`src/slic3r/GUI/JusPrin/Workspace/Workspace.hpp` about lines 126 to 129 and `WorkspaceSlicing` at 209), cleared when that plate slices. Reuse the issue monitor's record rather than deriving the message again; if the monitor is the better single source, give the adapter a way to read it, and say in the report why you chose that seam. Because the `<workspace>` block on every message and the slicing section of every tool reply are built from the snapshot, the reason then reaches the model whether the model or the person started the slice, with no second path. `slice_report` for an invalid slice carries it too. Keep the model's view of the slicing section short: severity, OrcaSlicer's message, setting, object; `slice_report` stays the full report.

**B. Event-driven `slice_start`.** After posting the slice event, decide synchronously from the snapshot which of three things happened: a run began, nothing was needed because the plate was already sliced and unchanged, or OrcaSlicer refused. Without `wait`, a refusal returns `started: false` with the reason, in a `succeeded` call, and the description's "returns once it has started" says what happens when OrcaSlicer refuses. With `wait`, finish the call from the workspace-change subscription when the run that began ends, or at once when a refusal is recorded, and keep one timer only for a run that never reports; `invalidate_pending` already finishes activities from inside that same callback (about line 2018), so the path is known. Remove the `SliceWait` polling and its duplicate `seen_running` bookkeeping. This fixes the "slice reports success with nothing sliced" and "hangs on retry" faults seen live on 2026-10-15. Kenneth's 2026-10-15 ruling stands: no handling of one particular cause; this passes on OrcaSlicer's words for every cause at once. The preview path not running validation is out of scope.

**C. The skill.** `skills/<name>/SKILL.md` with a trigger for this event, fired on the request where the model first reads the failure: the continuation request carrying the `slice_start` reply, or, when the person sliced from the button, the next request after the snapshot first shows a new failure on a plate (fire once per failure, not on every later message). The body opens with "The rules above still apply" and holds only what the model lacks: that OrcaSlicer's validation alone has about 150 distinct messages (`src/libslic3r/Print.cpp`, `Print::validate`) and the model should not assume it knows them; how to read one: the setting key names what to change and `settings_search` or `settings_get` tells what it is, the object narrows where; the difference between a refusal (nothing was sliced; change the named setting or the filament and plate pairing, then slice again) and a mid-run failure; that a problem counts as fixed only when a new slice no longer reports it; which decisions are the person's (a material versus a plate they own) and which the model can settle; and a short guide to the message families you find in `Print::validate`, grouped (layer height against nozzle, filament against plate type, outside the print volume, supports and rafts, multi-material and extruders, spiral vase and other mode conflicts), in the style of the notice table the model-arrived skill already has. Keep it well under the model-arrived skill's size. Nothing in it may restate a standing rule, and never write "approve", "authorize", "confirm before" or "ask the user then call again" anywhere; tool-call approval was removed on 2026-10-07.

If any sentence of today's standing prompt (`AgentUI/src/projectInstructions.fixture.txt`) is now carried by the fact or the skill, delete it and update the fixture; the prompt may not grow.
