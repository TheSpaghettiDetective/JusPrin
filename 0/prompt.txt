<result>I found two bugs that would leave existing chats permanently unusable in the shipped app, and two more that can do the same. The growth is only partly justified. I read the code at `claude/cache-r7-record-e80b27` without building or running anything, so every finding below comes from reading. Line numbers are on that branch.

### 1. Correctness

1. **Every chat migrated from before this change throws on its first request.** `start_chat_record` stores the migrated items with `format: ""`. On the very next line of the same turn, `ProviderAgent::begin_transcript` (`ProviderAgent.cpp:239-241`) throws `logic_error` because `format != wire_format(family)`. It only checks that the item list is non-empty, not that the format is non-empty. That covers every chat that has an earlier reply with text, on both providers. The exception leaves `begin_stream` with `m_stream` still set and goes to GUI_App's handler. The same throw then happens on every later message in that chat. The migration test (`test_agent_bridge.cpp` "a chat from before the record…") uses `RecordingAgent` rather than `ProviderAgent`, and even asserts `first.record.format.empty()` with two items. It records exactly the input that crashes the real loop. Fix: compare formats only when the format is non-empty.

2. **The production history cleanup deletes every picture and PDF the record keeps.** Blobs go to `&lt;projects&gt;/&lt;id&gt;/attachments/chat-&lt;conv&gt;/…` (`AgentHost.cpp:2758-2769`). After every model version, `ProjectAutosave::trim_history` (`ProjectAutosave.cpp:433-440`) calls `ProjectVersionStore::prune`. Its last loop (`ProjectVersionStore.cpp:987-993`) removes every file under `attachments/` that is not in the document's `attachments` index or `live_attachments`. Chat-record blobs are in neither.
   - After that, `load_record_bytes` (`AgentHost.cpp:2829`) gets `""` back from `read_attachment_blob`, which returns empty for a missing file (`ProjectPersistence.cpp:522-533`).
   - It then sends an image or document block with empty data. Because the record is append-only, every later request in that chat fails.
   - The "reopened project" test runs on in-memory persistence and never touches the version store.
   - A forked managed identity (`ProjectPersistence.cpp:318-333`) copies only the attachment folder from the opened file's auxiliary directory. The old project's managed `chat-*` blobs are not carried over.

3. **A request is recorded when the transport takes it, not when the provider accepts it.** `post()` calls `record()` as soon as `m_transport-&gt;post` returns true (`ProviderAgent.cpp:406`). By then the person's message, workspace block, pictures and PDFs are all in the record (see `m_settled` at :257/:300).
   - If the provider then answers 413 (`request_too_large`), or 400 for a bad or oversized image or PDF, that chat can never send again.
   - Before this change, earlier turns' attachments were stripped, so a bad attachment broke only its own turn.
   - The loop test "a turn whose request fails" asserts that the message is kept after a failure. It treats a 503 and a 400/413 the same, so this case is encoded as valid.
   - There is no size limit and no way to recover. Context or size overflow in a long chat (workspace block per turn, every picture, thinking blocks) is the same permanent failure, with only a generic error shown.

4. **Responses reasoning items are now replayed across turns with `store:false`.** They go back with their ids and no `encrypted_content` (`ResponsesCodec.cpp:72-76`, `:155`; no `include` is requested). Community reports describe a 404 "Item … not found. Items are not persisted when store is set to false" for exactly this. If that is right, the failure is now permanent per chat (append-only) instead of one turn. This is unverified against a live API and the author lists it as unverified, but it needs a live check before merge, not after.

5. **Retrying a failed reply that is not the newest sends a request that ends on the assistant.** In `make_agent_request` (`AgentHost.cpp:2967`), `request.source.empty()` returns early. `turn_recorded` (`ProviderAgent.cpp:263`) adds nothing. So the request is the record plus skills, and the record ends with a later turn's assistant item. `handle_retry` does not check that the retried message is the newest. On Anthropic this is an assistant prefill, which some models reject; on Responses it asks for a reply to nothing. Before this change, a retry always ended on the person's words.

6. **`turn_recorded` re-derives "already sent" from `attempt &gt; 1 &amp;&amp; source.empty()`.** The host already knows this exactly through `sent(user-&gt;id)`. These are two separate decisions about one fact, and only the host's is grounded in the record. Pass the fact, or have the host leave out the workspace.

7. **A rewritten note is sent again only when it starts the turn.** The `rewritten` check (`AgentHost.cpp:2892`) runs only for `user`. A rewritten note elsewhere in the chat is skipped by `sent()` in the unsent loop. Each re-send also appends a duplicate id to `messages` (`ProjectStateDocument.cpp:902`).

8. **Persistence costs grow per turn.** Each turn start parses the whole record three times: `start_record_of_earlier_chat`, `record_refusal`, `make_agent_request`. It also re-reads and base64-encodes every blob the chat ever sent, synchronously on the GUI thread. `publish_document` re-parses and re-dumps the whole state on every write. Attachments are stored twice, once as the attachment and once as a chat blob, and could be referenced instead.

Byte-exactness of rendering, the double-append and skipped-item paths, and thread safety: no finding. Rendering depends only on the record and the profile, the `m_recorded`/`m_settled` bookkeeping is sound, and everything runs on the GUI thread.

### 2. Error-handling discipline

9. **A missing blob silently becomes an empty picture.** `load_record_bytes` relies on `read_attachment_blob`'s "missing file returns empty". That turns a violated invariant into a silent wrong request, and it is what makes finding 2 invisible until the provider rejects it.

10. **The record is written strictly but read leniently.** In `ProjectStateDocument.cpp:92-104`, `record_part_from` treats any non-text, non-image entry as a PDF and defaults `blob`/`mime` to `""`. Meanwhile `record_part_json` throws on an empty blob, and `record_item_from` throws on an unknown kind. Reading should use `at()` and throw on an unknown part kind. `chat_record` has the same leniency with `value("format"/"messages")`.

11. **A reply request with no record sink silently keeps nothing.** In `ProviderAgent::record()` (:329), `!m_on_recorded` is a quiet no-op for replies. That is an invariant violation, since only titles may lack a sink.

12. **Fallible disk I/O runs after the request is already in flight.** The blob-write failure is thrown from inside `on_recorded` (`AgentHost.cpp:2768`), which `post()` calls after dispatch. The exception unwinds through `start()`/`poll()` and leaves `m_busy` true with a live request and `m_stream` set. Propagating is fine; the ordering is the problem.

13. **The same format invariant is checked in three layers.** `record_refusal` in the host, `begin_transcript` in the agent, and `append_chat_record` in the document. Keep the document's check and the host's refusal, and drop the agent's or make it the only pre-send check. The duplication also hid finding 1, because the three disagree on what an empty format means.

### 3. Growth that is not needed (about 70–90 production lines)

14. **The migration duplicates the unsent classification.** `start_record_of_earlier_chat` repeats the file-report / user / note if-chain and the literal report string (`AgentHost.cpp:2816` vs `:2887`). Merging them saves about 15 lines.

15. **`record.messages` mostly duplicates the item `source` fields.** Store only the ids the migration covered and derive the rest from the items. That saves about 10 lines and removes the duplicate data in state.json. `start_chat_record` is `append_chat_record` with an empty format plus covered ids, so merging them saves about 12 lines.

16. **Two parallel traversals.** The `keep` lambda and `load_record_bytes` walk the same parts and result images. One `for_each_blob(items, fn)` saves about 8 lines. Holding raw bytes in `RecordPart` would also drop the base64 encode/decode/re-encode round trip.

17. **The host and the agent split building the person's side.** The host builds `AgentUnsentMessage` plus `source`, `note`, `user_text` and `issue_context`, and the agent turns them into `RecordItem`s (`ProviderAgent.cpp:243-307`). The host could hand over ready-made items and let the agent add only the workspace and skills. That deletes `AgentUnsentMessage`, two request fields and about 25 agent lines. It also deletes the test-side copy of that logic in `kept_turn.hpp` (76 lines), which already differs from production: it keeps `issue_context` untagged, where production wraps it in `&lt;print_issue&gt;`.

18. **Unreachable fallbacks after exhaustive switches** in `record_kind_name`, `part_block` and `input_part`. These are small.

### 4. Test quality

19. Most new tests pin today's ordering and output rather than the transitions that matter. Untested:
    - the real `ProviderAgent` given a migrated record (finding 1);
    - on-disk persistence through autosave and prune (finding 2);
    - a 4xx after acceptance, and what the next turn sends (finding 3);
    - a host-level retry after the record holds the message: `RetryingAgent` never calls `on_recorded`;
    - a stop or failure followed by a new turn under the history-prefix guard (the guard scripts only successful turns);
    - retrying a failed reply that is not the newest.

    The fakes built on `kept_turn.hpp` produce records the real loop would never produce, so the host tests can pass while production differs.

**Verdict:** The storage and settlement code is inherent and justified (roughly the +226 and +73). About 70–90 lines are duplication. The record also brings in permanent per-chat failure modes (findings 1–4) that the old rebuild could not have, and these need fixing before the growth question matters.
