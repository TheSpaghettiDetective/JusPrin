## Reasons and tradeoffs

**Sourced:**
- **Microsoft Mixed Reality guidance.** The bounding box shows the object's full extent, so an object snapped to a surface doesn't seem to have phantom space around it. The toolbar stays on the side nearest the user so it is never blocked. This is the clearest precedent for docking a toolbar to a selected 3D object, and it is attached to a 3D box.
- **Godot.** The see-through box stays visible behind other objects while "still having a sense of depth" (PR above). An open proposal says axis-aligned boxes are "visually misleading" on non-box-shaped meshes and look bigger than the mesh: https://github.com/godotengine/godot-proposals/issues/14064
- **VR highlighting study.** Thin outlines were often too easy to miss, and tinting the whole object hid its details: https://arxiv.org/html/2403.15321

**My reasoning (no source found):**
- PowerPoint, Keynote and Paint 3D can use a 2D box because the model is a page element: the frame is its footprint on the page, and rotating turns the model inside that frame instead of moving a scene camera.
- In a slicer, a box around the projected silhouette changes size and shape every time the camera orbits. The toolbar docked to it would jump around.
- On a crowded plate, neighbouring boxes overlap and it becomes unclear which object is selected.
- A flat box says nothing about height or where the part touches the bed, which matter for printing.
- In its favour: it is always readable, easy to anchor a native toolbar to, and familiar from 2D design tools.
- If you keep the 2D box, I'd suggest computing it from the 8 projected corners of the 3D bounding box, keeping the toolbar inside the viewport, and hiding both while the camera orbits or the object is dragged.</result>

## 1. How the selection indicator is drawn

**Corner brackets**
- `Selection::render` is at `src/slic3r/GUI/Selection.cpp:2001-2013`. It takes the box and transform from `get_bounding_box_in_current_reference_system()` and colours the brackets `ColorRGB::WHITE()`, or `YELLOW()` on the assemble canvas (line 2011). The colour is hard-coded, with no config.
- It is called from `GLCanvas3D::_render_selection` (`src/slic3r/GUI/GLCanvas3D.cpp:8297-8306`), and only when no gizmo is running. That is the three call sites at `GLCanvas3D.cpp:2084/2091/2104`.
- `Selection::render_bounding_box` is at `Selection.cpp:2619-2771`:
  - Each bracket arm is 20% of the box size on that axis (`0.2f * box.size()`, line 2630). That makes 48 line vertices, 3 arms at each of 8 corners (lines 2641-2695).
  - If `auto_drop` is false, it adds down-arrows under the 4 bottom corners (lines 2698-2731).
  - The geometry is cached in `m_box` and rebuilt only when the box or `auto_drop` changes (line 2624).
  - Line width is `glLineWidth(2.0f * m_scale_factor)` on compatibility profiles (line 2747). On core profiles it uses the `dashed_thick_lines` shader with `width = 1.5f` and `gap_size = 0` (lines 2749, 2763-2764). GLES uses `dashed_lines`.
  - The colour comes in as a parameter and is applied with `m_box.set_color(to_rgba(color))` (line 2768).

**Mesh tint**
